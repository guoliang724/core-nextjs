# Next.js App Router Four-Layer Cache Architecture & Dynamic Invalidation (Full Verbatim Translation)

## 1. Four Layers of Caching

One layer is on the client side (browser), and three layers are on the server side (Node.js server).
We can break down each layer from the outside in along the path of a request from **"Browser -> Server -> Database"**:

```text
[ Client Side (Client) ]
  ├── 1. Router Cache (Browser Memory)
  │      └─ Checkpoint 1: Is the RSC for this page in browser memory? If yes, open instantly without touching the network wire.
  │
====================== Network Boundary (Network) ======================
  │
[ Node.js Server Side (Server) ]
  ├── 2. Full Route Cache (Server Disk)
  │      └─ Checkpoint 2: Request arrives at server—is compiled static HTML / RSC in disk? If yes, throw directly to browser.
  │
  ├── 3. Request Memoization (Server Memory)
  │      └─ Checkpoint 3: During code execution, was this fetch called just now in the same request? If yes, reuse memory value, refusing duplicate requests.
  │
  └── 4. Data Cache (Server Disk)
         └─ Checkpoint 4: Are cross-request API/data fetch results still on disk? If yes, bypass external API/DB and read directly.

```

---

### 1. Router Cache (Client Router Cache)

* **Location**: Browser Memory (Client In-Memory)
* **What it stores**: RSC Payloads of previously loaded page components. When you click `<Link>` to switch pages, Next.js pre-stores the new page's RSC into browser memory.

#### 1. Activation & Role

When you click the browser's "Back / Forward" buttons, or revisit links you just clicked, the page completes a seamless instant switch (opens in milliseconds), completely avoiding sending network requests to ask the server.

#### 2. Invalidation & Refresh Strategy

* **Automatic Invalidation (Time Control)**:
* Static Routes: Cached for **5 minutes** by default.
* Dynamic Routes: Cached for **30 seconds** by default.


* **Manual Force Refresh**:
* Calling `router.refresh()` on the client side (this clears current Router Cache and re-fetches from the server).
* Executing a Server Action containing `revalidatePath` or `revalidateTag`.
* A full page hard refresh (**Hard Refresh / F5**) directly wipes out browser memory.



---

### 2. Full Route Cache (Server Full Route Cache)

* **Location**: Server Disk / Memory (Server Disk / Memory)
* **What it stores**: Pre-rendered complete HTML pages + RSC Payload generated during Build Time or ISR incremental generation.

#### 1. Activation & Role

It corresponds to the **"Static Rendering"** discussed earlier. When a user visits a static page, the server does not need to re-execute any React component code or SQL queries; it serves the pre-cached HTML directly to the browser with extremely high performance.

#### 2. Invalidation & Refresh Strategy

* **Automatic Invalidation**:
* **Build Redeployment**: Every time the project is re-bundled and deployed, this cache is wiped clean.
* **ISR Timed Invalidation**: If `export const revalidate = 60` is set in the page, when a new request arrives after 60 seconds, the server regenerates that route's cache in the background.


* **Manual Force Refresh**:
* Calling `revalidatePath('/blog')` or `revalidateTag('posts')`.


* **When does it NOT apply?**:
Whenever a route switches to **"Dynamic Rendering"** (for example, using `cookies()`, `headers()`, or `cache: 'no-store'`), Full Route Cache is bypassed completely.

---

### 3. Request Memoization (Server Request Memoization / Function Deduplication)

* **Location**: Server Memory (Server In-Memory)
* **What it stores**: Data results returned by `fetch` within the lifecycle of a single HTTP request (Rendering Pass).

#### 1. Activation & Role

Solves the traditional **"Prop Drilling / Duplicate Data Fetching"** dilemma.

Suppose in three Server Components—`layout.tsx`, `page.tsx`, and a deeply nested `Header.tsx`—you all invoke `fetch('[https://api.com/user](https://api.com/user)')`:

* **Traditional Approach**: You must `fetch` once at the top level and pass down props layer by layer to child components.
* **Next.js Mechanism**: You can fearlessly write `fetch` inside each of these three components directly. When React processes this request, it only issues an actual outward API request for the first call; the subsequent two calls hit Request Memoization and return from memory in milliseconds.

#### 2. Invalidation & Refresh Strategy

* **Extremely Short Lifecycle**: Its lifecycle is restricted strictly to a **"single render request."**
* The moment the server finishes generating the RSC Payload for this request and responds to the browser, this cache is destroyed immediately. It does not cross requests, nor does it cross users.

---

### 4. Data Cache (Server Data Persistent Cache)

* **Location**: Server Persistent Storage (Server Persistent Storage / Disk)
* **What it stores**: `fetch` response data (JSON/API results) across requests and users.

#### 1. Activation & Role

This is the core of Next.js extending the native `fetch` API.
When writing `fetch('https://...')` in a Node.js environment, Next.js intercepts this request:

* By default, it saves the data returned by the API onto disk.
* When the next user—or even a user visiting tomorrow—initiates a request, as long as this data hasn't expired, the server won't even call external APIs; it reads the Data Cache directly off disk.

#### 2. Invalidation & Refresh Strategy

* **Time-based Revalidation**:
```typescript
// Serves Data Cache within 60s; requests after 60s trigger background updates
fetch('https://api.com/data', { next: { revalidate: 60 } })

```


* **On-demand Revalidation**:
```typescript
// 1. Attach tag
fetch('https://api.com/data', { next: { tags: ['collection'] } })

// 2. Precisely sever cache in Server Action or Route Handler
revalidateTag('collection')

```


* **Explicit Disabling (No Store)**:
```typescript
// Bypasses Data Cache completely, calling real endpoint every single time
fetch('https://api.com/data', { cache: 'no-store' })

```



---

### Summary: Panoramic View of Four-Layer Cache Collaboration

Suppose a user clicks a link to visit `/posts`. The decision chain for the entire cache evaluation operates as follows:

1. **Check Router Cache (Client)**: Is the RSC for this page in browser memory?
* **Yes**: Displays instantly (opens in milliseconds), process ends.
* **No**: Sends network request to server.


2. **Check Full Route Cache (Server)**: Is there pre-compiled static HTML/RSC for this route on server disk?
* **Yes**: Directly returns pre-compiled Payload, process ends.
* **No**: Server prepares to begin dynamically executing React component code.


3. **Execute component code; encounters `fetch**`:
* **First check Request Memoization (Server Memory)**: In this exact same render pass, did I just call this identical `fetch`? If called, directly serve memory value.
* **Next check Data Cache (Server Disk)**: Has this `fetch` URL been called by previous requests? Has the cache expired?
* **Unexpired**: Reads data directly from Data Cache without making actual network requests.
* **Expired / Uncached**: Initiates real external API/database request, writes result to Data Cache, and puts it in Request Memoization for reuse in the same render pass.





Mastering the mutual exclusivity and collaboration of these four caching layers gives you crystal-clear clarity when troubleshooting App Router issues like *"Why hasn't data updated?"* or *"Why didn't the page change in real-time?"*!

## 2. Secondary Dynamic Adjustment: `revalidate`

### 1. Manual Dynamic Control (Runtime Invalidation)

`revalidatePath` and `revalidateTag` are **active intervention switches** held in your hands at runtime.

* **Role**: System manual control lever / emergency brake.
* **Characteristics**: When a write operation occurs (such as a Server Action updating the database), you use them to break original Level-1 configuration rules, forcing all Level-1 caches corresponding to a certain path (`Path`) or data tag (`Tag`) to be purged, thereby forcing the system to fetch the latest data immediately.

### 2. Which Caches Do `revalidate` Change?

`revalidatePath` does not "modify" cache mechanism configurations; instead, it acts as a **precision scalpel** to actively invalidate/purge corresponding cached data:

1. **Purges Data Cache (Server Disk)**:
* Finds underlying `fetch` static data caches associated with that path and marks them as invalidated. Upon next render, forces a fresh re-fetch from the real database/endpoint.


2. **Purges Full Route Cache (Server Disk)**:
* Purges pre-generated HTML / RSC static files for that path.


3. **Purges Router Cache (Client Browser)**:
* Because this action happens inside a Server Action response, Next.js informs the frontend in response headers: *"Erase the Router Cache stored in browser memory for the `/posts` node, and replace it with the latest RSC Payload I send you this time."*



* **Note**: It alone does not need to handle Request Memoization, because Request Memoization automatically self-destructs anyway as the single request completes.
