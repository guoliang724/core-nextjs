# SSR Architecture, Custom SSR Implementation

## 1. SSR vs CSR

### 1. CSR Process

![avatar](/imgs/CSR.png)

```text
Browser                                           Server
   │ ───────────────── 1. Request ────────────────> │
   │ <─────────── 2. Empty HTML Response ───────── │ (White Screen state)
   │ ── 3. Multiple Requests (CSS, Images, JS) ───> │
   │ <────────── 4. Resource Responses ─────────── │
   │
   [ 5. Execute JS ]
   │
   [ 6. Render Page ]

```

#### Disadvantages of CSR:

1. The browser stays in a white screen state for a while.
2. Not good for SEO.

   │ <────────── 5. Resource Responses ─────────── │
   │
   [ 6. Execute JS ]

   [ 7. JS takes control over subsequent process ]

## 2. Build It!

### 1. Setting Up an Express Server

Server generates HTML string and sends the generated HTML string to the client.

```javascript
const express = require("express");
const app = express();

app.get("*", (req, res) => {
  const html = `
  <!DOCTYPE html>
  <html lang='en'>
    <head>
      <meta charset='UTF-8'/>
    </head>
   <body>
      <div id='root'>
         hello
      </div>
   </body>
  </html>
`;
  res.send(html);
});
```

### 2. Server to Render React

Using `renderToString` from `react-dom/server` to convert React components into strings.

```javascript
import Home from "./pages/Home";

// ReactDom.render(<Home/>, document.getElementById("app"));
const componentHTML = ReactDom.renderToString(<Home />);

// pages/Home/index.jsx
import React from "react";

export default function () {
  return <h1>Home</h1>;
}
```

#### Problems:

1. Node.js does not recognize `import` and `from`.
2. Node.js does not recognize JSX expressions.

#### Solution:

Webpack resolves file paths through the `fs` module. Whether using `import` or `require`, they are only responsible for providing clues. Webpack reads everything into strings (modules) using the `fs` module for storage.

Using Webpack + Babel to resolve Node.js's inability to recognize JSX expressions:

```javascript
// webpack.config.js
module.exports = {
  mode: "development",
  watch: true,
  module: {
    rules: [
      {
        test: /\.jsx?$/,
        use: {
          loader: "babel-loader",
          options: {
            presets: ["@babel/preset-react"],
          },
        },
        exclude: /node_modules/,
      },
    ],
  },
};
```

When using Webpack for the server, you must inform Webpack of the target Node.js environment.
Webpack's default build target is the browser environment (`'web'`).

- **Built-in module processing failure**: Node.js has many native core modules, such as `path`, `fs`, `crypto`, `stream`, etc. These do not exist in a browser environment. If the `target` is set to `'web'`, when Webpack tries to resolve `import path from 'path'` in the code, it will throw an error indicating the module cannot be found, or bundle it as an empty object.
- **Runtime glue code**: When outputting bundled files, Webpack wraps its own "loader function (Runtime)" at the top. The implementation logic of this runtime glue code is completely different for browsers versus Node.js (for example, handling dynamic `import()` resource loading uses `<script>` tags in browsers, but uses `fs.readFileSync` in Node).

When using Webpack for Node, consider preventing Webpack from bundling third-party dependencies under the `node_modules` directory into the final output file, keeping them as external dependencies (`externals`). This is because the server's own runtime environment already contains `node_modules`.

```javascript
const nodeExternals = require('webpack-node-externals');

module.exports = {
  ...

  target: 'node', // Explicitly inform Webpack that the build target is the Node.js environment

  // Critical configuration: Automatically scan node_modules and exclude them from bundling
  externals: [nodeExternals()],

  ...
};

```

### 3. Client to Render React

#### Why is Client-Side Rendering of React Needed?

Pages rendered by the server have no DOM event listeners, no interactivity, and no active client state.
After the browser receives the HTML, it requests JS, executes JS, and takes control over interactivity.

![avatar](/imgs/client-render.png)

#### Goal: Maintain consistency between server and client rendering (i.e., Isomorphism)

**Hydrate**:

```javascript
// ReactDom.render(<App />, document.getElementById('root'));
ReactDom.hydrate(<App />, document.getElementById("root"));
```

### 4. Adding Styles

#### Purpose:

Utilize Webpack to generate style files, ensuring that when CSS styles are imported in client components and server components, class names remain consistent. Client and server are bundled separately using Webpack:

- **Client**: Has complete style dependencies. Processed via `css-loader` and `mini-css-extract-plugin` to generate CSS bundle files.
- **Server**: Does not need complete style dependencies, but must ensure that generated class names match the client. The server Webpack build uses `isomorphic-style-loader` or `css-loader` to extract hash class names and insert them into the server HTML page.
- Add a `<link>` element in the HTML source code referencing the CSS stylesheet.

#### Problems:

**Where should global CSS files be imported—on the client or server?**
Because global styles do not involve CSS Modules, importing them exclusively on the client side is feasible:

```javascript
import "../assets/global.css"; // ✅ Valid

export default () => {
  return <Home />;
};
```

```javascript
import styles from "../assets/global.css"; // ❌ Invalid for CSS Modules pattern

export default () => {
  return <Home classNames={styles.someStyle} />;
};
```

**Local Styles (CSS Modules)**:
Because local styles involve CSS Modules, CSS class names used in client components might differ from those in server components if not synced.
This is resolved via `isomorphic-style-loader`. The client Webpack is responsible for generating CSS files, while the server Webpack build ensures that class names inserted into the rendered page match the client exactly (e.g., `<div class="beu-581abe0f"></div>`).

## 8. Traditional SSR's "Hydration Pain Points"

### 1. "All-or-Nothing Hydration":

#### Hydration Summary:

Hydration is a **once-only process** that occurs strictly during initial page load.

After successful hydration, your application turns into a standard Single Page Application (SPA). All subsequent updates are handled by the framework's declarative reactive system, completely independent of the server.

The core problem solved by classic SSR is indeed **First Contentful Paint (FCP) / Largest Contentful Paint (LCP) speed and SEO**.

In traditional Next.js (Pages Router) or standard SSR, hydration suffers from a major bottleneck known as **"All-or-Nothing Hydration"**:

- **Large Bundle Size**: For the client to hydrate the whole page, JS code for all components rendered on the server must be downloaded to the browser.
- **Blocks Interactivity**: Before client JS finishes downloading, parsing, and executing hydration, the page remains non-interactive even if it looks fully rendered (clicking buttons produces no response).

---

### 2. Next.js Core Architectural Evolution: Cutting and Restructuring Hydration

Particularly since Next.js 13+ introduced the **App Router** and **React Server Components (RSC)**, the mechanism relies on "component-level granularity splitting" and "streaming" to reduce hydration costs dramatically, or bypass hydration entirely!

#### ① Zero-Bundle-Size & RSC (React Server Components)

In Next.js App Router, components default to **Server Components**.

- Server Components execute strictly on the server, sending pure HTML/RSC Payload directly to the client.
- The JS code for these components is **never bundled or sent to the browser**!
- Since the client lacks the JS for these components, **they require zero client-side hydration**.
- Only interactive nodes marked with `"use client"` (such as buttons, form inputs) bundle JS and send it to the client for Hydration.

> **Effect**: ~80% of static page content no longer participates in hydration, drastically reducing client JS bundle size and CPU load.

#### ② Selective Hydration & Streaming

Leveraging React 18's `<Suspense>`, Next.js supports streaming rendering and selective hydration:

- Pages do not need to wait for all API requests to complete before starting hydration.
- Slow components (e.g., a comments section) wrapped in `<Suspense>` allow main content to render and hydrate first, making it interactive immediately.
- Once comment data finishes loading, it streams to the browser to perform isolated local hydration on the comments section.
- If a user clicks an unhydrated comments section while it's loading, React **boosts the Hydration Priority** for that targeted region.

#### ③ "Server-Driven Navigation" Incremental Updates

The update phase undergoes a major evolution under Next.js App Router:

- When navigating from `/page-a` to `/page-b`, Next.js does not recreate all Page B components on the client like a traditional SPA.
- Next.js issues a lightweight request to the server, and the server returns the **RSC Payload** (a compact JSON tree description) for Server Components in Page B.
- The client router replaces or merges the current view tree using this new RSC Payload.
- If Page B contains Client Components, **only newly inserted Client Components undergo local hydration**.

---

### Summary:

- **Traditional SSR**: "Sends a massive heap of HTML and JS on initial load; client hydrates the entire page at once; subsequent updates handled by client SPA."
- **Next.js Architectural Upgrade**: "Initial load sends JS _only_ for components requiring interactivity, while static components skip hydration entirely; subsequent page updates and interactions use RSC Payload for fine-grained streaming incremental replacement, performing local hydration strictly on newly added interactive nodes."

Next.js does not make hydration span across the update phase—instead, it uses React Server Components technology to **virtually eliminate the presence and overhead of hydration**.
