# Next.js Image Optimization & CSS Pixel Mechanics (Full Verbatim Translation)

## 1. Underlying Optimization Logic of the `<Image/>` Component

### 1. Combining Screen Size to Request Different Image URLs

Next.js calculates the total physical pixels required by combining **CSS pixels ✖️ Device Pixel Ratio (DPR)**.

Then, it selects a physical pixel size from the `srcset` list that is closest to (and not smaller than) the required pixels.

```html
<img
  src="/_next/image?url=%2Fhero.jpg&w=1080&q=75"
  srcset="
    /_next/image?url=%2Fhero.jpg&w=640&q=75 640w,
    /_next/image?url=%2Fhero.jpg&w=750&q=75 750w,
    /_next/image?url=%2Fhero.jpg&w=1080&q=75 1080w
  "
>

```

1. The browser selects the appropriate size for itself based on `srcset` and issues a URL request to Next.js with a specific width (such as `?url=hero.jpg&w=828`).
2. **Server-Side Dynamic Cropping**: Upon receiving this GET request, Next.js's Node.js backend:
* **If cached**: Checks if a "WebP version of `hero.jpg` with a width of 828px" already exists in local/memory cache. If cached, it returns the cached image directly to the browser (in milliseconds).
* **If uncached (first visit)**: Finds the original `hero.jpg` (assuming the original image is a large 4000px image), uses an underlying image processing library (like `sharp`) to crop it in real-time to an 828px width, compresses and converts it into WebP/AVIF format, saves it to cache, and returns it to the browser.



### 2. Converting JPEG / PNG to WebP or AVIF

Next.js's Node.js server (powered by the high-performance `sharp` library) dynamically converts large original images into WebP or higher-compression AVIF upon receiving requests.

Under the premise that the human eye cannot perceive minute differences, it typically cuts the image file size directly by **30% ~ 70%**.

### 3. Pre-defining Container Dimensions to Prevent Page Jumps (CLS)

This addresses **CLS (Cumulative Layout Shift)** in Web Performance metrics.

Traditional images have a height of 0 before loading, and the moment they finish loading, they abruptly push down the text below, causing a terrible user experience.

By mandating `width` / `height` inputs or using `fill` layout alongside a parent container, Next.js enables the browser to stretch open the placeholder box in the DOM tree before a single byte of the image is even downloaded (setting the aspect ratio).

### 4. Fetching Base64 Image Color Blocks in Advance (Placeholder)

If `placeholder="blur"` is set, Next.js encodes an extremely tiny thumbnail into a Base64 string at build time (for static images) or via your provided `blurDataURL`, embedding it directly into the HTML's CSS background.

* **Advantage**: **0 network requests**. As soon as the page refreshes, the minimal blurred color block appears instantly, gracefully transitioning once the high-resolution image finishes downloading.

                                │

## 2. Physical Pixels vs. CSS Pixels

### 1. Physical Pixels

Physical pixels refer to the actual hardware pixel dots present on the display screen when the device leaves the factory.
These pixel dots are fixed at manufacturing and will never change throughout their lifecycle.

### 2. CSS Pixels

CSS pixels are the "visual units" or "visual dimensions" promised by the browser to developers.
Official definition of how large a CSS pixel is: **`96 px = 1 in = 2.54 cm`**.

### The Ultimate, Truly Crucial Sentence:

> **The browser does only one thing: it maintains constant visual size—that is, keeping CSS pixels constant—rather than keeping physical size constant.**

Browsers and hardware manufacturers smooth out two layers of differences for developers: "different physical PPI across screens" and "different viewing distances of users." Developers only need to write `font-size: 16px`, and the browser ensures that whether on a smartphone 30 cm away from the eyes or a TV 3 meters away, users perceive text and graphic sizes consistently, clearly, and comfortably at their respective viewing distances.

## 3. What Purpose Do `width` and `height` Serve in the `<Image/>` Component?

1. `width` and `height` do not lock the image into specific fixed pixels; instead, they establish the image's **Aspect Ratio (`aspect-ratio`)**.
* With this aspect ratio, the backend server has a guideline when cropping images. If a large image with physical pixels of **4000 ✖️ 3000** has `width={800}` and `height={600}` set, and a `srcset` request asks for a scaled-down version with a width of **390px**, the height will automatically be **292.5px**.


2. **Generating a reasonable upper limit for `srcset**`: When Next.js automatically generates the `srcset` image list on the server (such as `640w`, `750w`, `828w`, `1080w`, etc.), it references the `width` you passed in:
* If you pass `width={400}`, Next.js knows: *"This image will display at a maximum CSS width of around 400px on the page (even accounting for a 3x screen, the maximum physical pixel demand is only 1200px)."*
* Next.js will then **not** generate unnecessarily large HD URL requests like `2048w` or `3840w` in the `srcset`, preventing superfluous oversized images right at the source, thereby saving server resources and network bandwidth.


3. **Local vs. Remote Images**:
* **Local Images**: Next.js automatically extracts original physical pixels —> automatically determines baseline aspect ratio (can be overridden manually).
* **Remote Images**: Cannot be automatically extracted —> you must explicitly specify `width` / `height` manually or use `fill` to define the aspect ratio.
